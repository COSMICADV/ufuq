# Phase 3 — Authentication & tenancy: status

**Roadmap reference:** DOCUMENT 25, Phase 3
**Exit criterion:** _the authorization matrix test passes for every implemented
endpoint, and the tenancy scope cannot be bypassed by omitting a `where`
clause._

**Status: complete.** Verified by the automated suites below — 89 tests
across three packages, including 19 end-to-end HTTP tests and a dedicated
row-level-security suite that queries with no `WHERE` clause at all and
proves the database itself, not application discipline, is what blocks a
cross-tenant read or write.

---

## Approved decisions this phase implements

| Decision                                           | Where it lands                                                                                                                           |
| -------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------- |
| UUID v7, generated by the application (OD-12)      | `@ufuq/db`'s `generateId()`; no Prisma model declares a default on `id`                                                                  |
| One user, one company in V1 (OD-01)                | `(company_id, email)` unique, not global; schema shaped so a membership table is additive                                                |
| Web cookies + mobile access/refresh tokens (OD-02) | One `sessions` table, `client_type` column; `ufuq_session`/`ufuq_csrf` cookies for web, Bearer + `POST /auth/refresh` for mobile         |
| One `sessions` table                               | `packages/db/prisma/schema.prisma` — `Session` model                                                                                     |
| PostgreSQL RLS + Prisma tenant isolation (AD-03)   | Every tenant-scoped table `FORCE`s row-level security; `ufuq_app`, the only role the running API ever authenticates as, cannot bypass it |

## What is complete

### `packages/auth` — pure domain logic, no framework dependency

The DOCUMENT 02 §4 permission catalogue (59 permissions) and role→permission→
scope matrix for the four V1 roles, transcribed table by table; `resolveScope`
(DOCUMENT 09 §4 check 4, ready for the first Phase 4+ scoped endpoint);
Argon2id password hashing with a constant-time dummy comparison for unknown
emails; opaque token generation/hashing; the DOCUMENT 09 §2 password policy
(length + a local breach list, no character-class rule DOCUMENT 09
specifically rejects).

### `packages/db` — schema, migration, RLS, seed

Prisma schema for `companies`, `roles`, `permissions`, `role_permissions`,
`users`, `sessions`, `password_reset_tokens`, `invitations`, `audit_logs`. One
hand-authored migration on top of Prisma's generated DDL: the `ufuq_app`
runtime role (least privilege — read-only on `permissions`/`role_permissions`,
no UPDATE/DELETE on `audit_logs`), `FORCE ROW LEVEL SECURITY` and a
`tenant_isolation` policy on every tenant-scoped table, and four
`SECURITY DEFINER` functions (`auth_lookup_login`, `auth_lookup_session`,
`auth_lookup_session_by_refresh_hash`, `auth_lookup_reset_token`,
`auth_lookup_invitation_token`) — the only, explicit, greppable way any query
runs before a tenant is known (DOCUMENT 09 §7). (2026-09-28: their
`search_path` is now pinned to `pg_catalog, public, pg_temp` with qualified
names, so a temporary table cannot shadow the real ones — migration
`20260928000000_auth_lookup_search_path`, see docs/PHASE-6-STATUS.md.) `withTenant`/
`withPlatformContext` are the sole way application code reaches the database;
both bind `app.company_id` with `SET LOCAL`, scoped to one transaction. The
idempotent seed script loads the permission catalogue and system roles
everywhere, and (outside `NODE_ENV=production`) a demo company and ADMIN
login, since Phase 3 has no company-registration or employee-creation flow
of its own yet to produce one.

### `apps/api/src/auth` — the endpoints

`POST /auth/login`, `/logout`, `/forgot-password`, `/reset-password`,
`/accept-invitation`, `/change-password`, `/refresh`, `GET /auth/me` —
DOCUMENT 08 §4.1, plus `/refresh` (see Decisions Required). Account lockout
(5 failures / 15 minutes, DOCUMENT 09 §1) and Redis-backed rate limiting
(DOCUMENT 08 §6) as independent controls. Session rotation on mobile refresh,
revocation on logout/password-change/-reset. `SessionAuthGuard` (DOCUMENT 09
§4 check 1, binds tenant scope), `CsrfGuard` (double-submit, DOCUMENT 20 §6),
`PermissionsGuard` + `@RequirePermission()` (check 3, ready for Phase 4+ —
no Phase 3 endpoint needs a specific permission). Every auth event DOCUMENT
21 lists under "Authentication & access" is written inside the same
transaction as the state change it documents.

## What is deliberately not here

- Sending an invitation (`POST /employees/{id}/invite`) — Phase 5.
- Delivering a password-reset email — Phase 15 (Notifications). The token
  lifecycle is complete; nothing yet carries the token to the user outside
  direct API/DB access.
- ~~`GET /audit-logs` (the read endpoint)~~ — not in this phase's explicit
  scope; the write path DOCUMENT 21 requires is complete. **Built
  2026-09-27** with `GET /audit-logs/entity/{type}/{id}` and the audit log
  screen; see docs/PHASE-6-STATUS.md, "Pre-Phase 7 cleanup".
- Company registration, employee creation, and therefore any UI a real admin
  would use to invite someone — Phases 4, 5, 16.
